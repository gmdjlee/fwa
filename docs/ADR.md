# ADR — 설계 결정 기록

각 항목은 **결정 / 맥락 / 대안 / 결과**로 기록한다. 뒤집으려면 새 ADR을 추가한다.

---

## ADR-1 · 종횡비는 3단 폴백으로 결정한다

**결정**
① 앱별 저장 프로파일 → ② 스크린샷 검은 띠 실측 역산 → ③ 사용자 프리셋 → ④ 기본 16:9

**맥락**
다른 앱이 재생 중인 영상의 종횡비를 직접 조회하는 API는 없다.
`MediaSession` 메타데이터에도 해상도는 없고, 앱마다 넣는 정보가 다르다.

**대안과 기각 사유**
- 사용자 수동 지정만: "모든 앱에 자동 적용" 요구사항 위반
- MediaProjection 상시 캡처: 배터리/발열, DRM 차단
- `MediaSession` 파싱: 커버리지가 너무 낮음

**결과**
②가 이 시스템의 "자동" 을 담당한다. `AccessibilityService.takeScreenshot()`(API 30+)은
DRM 화면에서 검게 나올 수 있으나, **검은 띠 측정에는 그 자체로 문제가 없을 수도 있다** —
DRM 프레임이 통째로 검게 나오면 감지 실패로 떨어지고 ①③④로 폴백한다. 안전한 열화다.

## ADR-2 · 고정 지연을 쓰지 않는다

**결정**
분할 진입 → 파트너 실행 → 디바이더 이동의 각 단계는 **조건 폴링 + 타임아웃**으로 넘어간다.
상태 머신은 순수 도메인이고, 시간은 외부에서 주입되는 이벤트다.

**맥락**
`postDelayed(600)` 류는 저사양 상태·저전력 모드·앱 콜드 스타트에서 무너진다.
이 앱은 "원터치로 항상 되는 것"이 유일한 가치이므로 재현성이 기능 자체다.

**결과**
상태 머신을 android 의존 없이 테스트할 수 있게 되어 실기기 검증 비용이 크게 준다.

## ADR-3 · 파트너 창을 낭비하지 않는다

**결정**
남는 창(16:9 기준 740px)은 검정 고정이 아니라 **콘텐츠 슬롯**으로 설계한다.
기본값은 검정, 옵션으로 시계 / 메모 / 사용자가 지정한 임의 앱.

**맥락**
사용자 스케치에서 파란 띠로 표현된 영역은 화면의 37%다. 이걸 그냥 검게 두면
"영상을 옮기는 앱" 이지만, 슬롯으로 만들면 "폴드 시청 레이아웃 앱" 이 된다.

**결과**
파트너 Activity는 임의 크기로 리사이즈될 수 있어야 한다(Android 16 적응형 동작).

## ADR-4 · domain 은 순수 Kotlin으로 유지한다

**결정**
`domain/` 에 `import android.*` 금지. 계산·상태·정책은 전부 여기에.

**맥락**
이 프로젝트는 실기기 검증 비용이 비대칭적으로 크다(폴드 실물 필요, 접근성 재설정, 앱별 확인).
JVM 테스트로 커버되는 표면적을 최대화하는 것이 유일한 저비용 방어선이다.

**결과**
`Rect` 대신 자체 `IntRect`, `Bitmap` 대신 `LetterboxScan` 같은 경계 타입이 필요하다.
약간의 변환 비용을 감수한다.

## ADR-5 · 배치 후 폐루프로 보정한다

**결정**
배치 완료 후 재측정 → 잔여 띠가 임계(8px) 이상이면 **1회만** 미세 조정.

**맥락**
앱마다 자체 상단바/컨트롤 오버레이 높이가 다르다. 계산값만으로는 마지막 몇 px이 남는다.

**대안과 기각 사유**
- 앱별 오프셋 테이블 하드코딩: 앱 업데이트마다 깨짐, "모든 앱" 요구사항 위반
- 무한 보정 루프: takeScreenshot 레이트 리밋과 충돌, 진동 위험

**결과**
재시도 1회 제한. 그래도 남으면 실패가 아니라 "근사 성공" 으로 보고하고 수동 조정을 안내한다.

## ADR-6 · Google Play 배포를 목표로 하지 않는다

**결정**
사이드로딩 전제. 접근성 서비스 사용 앱은 Play 정책상 심사 부담이 크고,
이 앱의 접근성 사용은 정당하지만 자동 심사에서 반복적으로 걸릴 가능성이 높다.

**결과**
Play 정책을 우회하려고 기능을 왜곡하지 않는다. GitHub 릴리스로 APK를 배포한다.
